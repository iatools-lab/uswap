fix(auth): rendre les invitations utilisables sans service e-mail

Contexte
Un compte cree en mode invitation (accountStatus=PENDING) ne recevait aucun
e-mail lorsque RESEND_API_KEY n'etait pas configuree : le compte existait bien
en base mais restait inactif, sans aucun moyen d'activation.

Corrections
- RegisterDto : le mot de passe n'est plus exige lorsque accountStatus vaut
  PENDING. Seul sendInvite etait pris en compte, or le frontend envoie
  accountStatus : toute creation de compte invitee echouait en 400.
- AuthService.register / resendInvitation : quand l'envoi echoue, la reponse
  expose desormais activationUrl pour que l'administrateur transmette le lien.
  Le champ est omis des qu'un fournisseur e-mail est configure, afin de ne
  jamais divulguer un jeton d'activation en production.
- EmailService : le lien d'action est journalise et l'avertissement precise le
  destinataire, au lieu d'un simple "service non configure".
- .env.example : documentation de RESEND_API_KEY / MAIL_FROM, des pieges du
  domaine d'envoi et de la procedure d'activation manuelle.

Outils ajoutes
- scripts/activate-user.cjs : active un compte en attente sans e-mail.
- scripts/fix-pending-accounts.cjs : traite les comptes en attente (active les
  comptes legitimes, supprime les comptes de test sans historique).
  Simulation par defaut, --apply pour executer.
- scripts/test-e2e.mjs : suite de tests fonctionnels (70 verifications)
  couvrant les 10 domaines du sprint 5.
- Suppression des scripts de diagnostic jetables (diag-*, tmp-db-pass).

Verifications
- tests e2e : 70/70
- cycle invitation complet : creation -> activationUrl -> activation -> connexion
- comptes en attente bloques : 13 -> 0
